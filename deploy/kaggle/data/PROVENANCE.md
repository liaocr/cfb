### ⚠ dev 从这一版起是**冻结**的（--dev-ids）

`tools/build-sft.mjs` 原本按**仓库哈希**切 dev。加新仓库会让 **dev 变大** ——
而 dev 一变大，上一轮在 89 条上跑出来的成绩就没法比了：两个数各自都对，
放在一起比就是错的，而且**不会以任何方式报警**。

所以这一版起用 `--dev-ids .cfb-offline/sft/dev-ids.txt` 把 dev 逐 id 钉死。
实测：89 个 id 全部找到、教师基线仍是 55/89 = 0.618（与冻结前逐字相同），
并挡掉 **134 条** dev 仓库的新单元 —— 同一仓库的多个单元高度相似，
让它们进训练集就是泄漏，而**泄漏只会让 dev 虚高、不会报警**。

> 历史版本：gen-ruler/4 是训练 412 / 教师基线 55/89 = 61.8%；
> gen-ruler/3 是训练 256 / 教师基线 31/89 = 34.8%。
> dev 集历次**完全一致**（89 条的 id/raw/ctx 逐条相同），所以旧的学生稿
> 仍可直接跟新基线配对比较。旧版数据在 git 历史里：
> `git show eb46fdc:deploy/kaggle/data/sft-train.jsonl`

**验证集故意不过滤。** 若先过滤再切分，dev 里只剩"教师本来就过尺子"的那部分，
学生哪怕只会照抄，通过率也天然接近 100%，跟教师 61.8% 的基线没法比 ——
那是一个只会报喜的指标。所以切分在过滤之前，`report.json` 里另记
`devTeacherPass` 当基线。**学生分数要跟 61.8% 比，不是跟 100% 比。**

训练集被拒的分布 —— 注意是**闸的命中数**，不是行数：一条稿子可以同时踩几个闸，

### 为什么 G7 不在这张表里（gen-ruler/4）

压缩比从硬门**下架、转软标准**（COMPRESSION_TARGET = 0.5）。四条实测理由：
24 条教师稿只挂 G7 一件事而软分与整体持平（0.6993 vs 0.703）；阈值 0.55 落在
分布内部没有自然断点；压缩本来就在软分 S4 里；**阈值一放宽，师生差距从 15.1 点
扩大到 41.1 点** —— 它一直在掩盖学生的缺口。详见 docs/RULER-V4-AND-G1-GUARD.md。

以后再训练到 0.5 时，把尺子的 COMPRESSION_HARD_MAX 设成 0.5 就重新装上。

### G0 的来历

**G0 是 gen-ruler/3 新加的，加之前那个 44.9% 是虚高的。**
所有闸原本都是**否定式**约束（不许编、不许抄、不许超长），没有一条要求稿子里
**必须存在**什么东西 —— 于是空字符串能过 16/89 = 18.0%。这 16 条都是 raw 里
没有文件路径、失败陈述里也没有承重锚点的单元，G1–G7 全部空转。
G0 补的就是这条：`load.length === 0 && !codeTask` → 拒。
升到 `gen-ruler/3` 后空稿得 0.0%，教师基线降到真实的 34.8%。

## 每行结构

```json
{"id": "...", "repo": "...", "system": "压缩提示词", "user": "[题面] ctx\n\n[思考过程] raw", "assistant": "压缩稿", "meta": {...}}
```

`system`/`user`/`assistant` 三段是**结构化**的，不写死分隔符 —— 由训练脚本调用底座原生
`apply_chat_template` 渲染。RWKV7 的模板是 `<|rwkv_tokenizer_end_of_text|>System: …\n\nUser: …\n\nAssistant: …\n\n`。
