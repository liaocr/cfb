## 一、缺陷一：分母里有 18% 的单元谁都过不了

`G0 no-leverage` 的条件是 `load.length === 0 && !codeTask` —— **只读 raw 和 ctx，不看稿子**。
实测：89 条里 G0 的命中，教师和学生**是同一批 16 条，一条不差**（不一致数 = 0）。

这不是「尺子严」，是**尺子被用在了它没有受力点的单元上**。任何稿子都过不了，
理论上限 73/89 = 82.0%。而尺子自己早有这道门 —— `preflight()` 的 P5 就是拦这类单元的，
但它拦在花钱之前，dev 从来没走过 preflight。

**修法**：G0 的结论提升成顶层布尔 `gaugeable`，`eval-sft.mjs` 用它当分母并做交叉校验
（教师/学生不一致就直接 FATAL）。不再靠解析 `'G0 no-leverage'` 这个字符串 ——
字符串一改措辞，分母就会静默错位，而分母错了没有任何指标会报警。

## 二、缺陷二：G7 是拍脑袋的阈值，而且和软分重复计数

- **24 条教师稿只挂 G7 一件事**，其余七门全过。它们的软分均值 **0.6993**，
  教师整体 0.703 —— 尺子扔掉的和留下的一样好。
- 这 24 条的 token 比从 **0.5834** 起跳。0.55 落在分布**内部**，那里没有自然断点。
- **压缩已经在软分里**：`S4_compressionGain`，权重 0.13。G7 是同一件事数了两遍。
- 三个数互相打架：prompt 要 **10~20%**，教师交 **~50%**，尺子容忍 **55%**。

### 阈值扫描（有受力点 73 条）

| G7 阈值 | 教师 | 学生 | 差 |
|---|---|---|---|
| 0.55（v3 的现状） | 42.5% | 27.4% | 15.1 |
| 0.70 | 60.3% | 32.9% | 27.4 |
| 0.85 | 68.5% | 34.2% | 34.3 |
| 不设限 | **75.3%** | **34.2%** | **41.1** |

**阈值一放宽，差距不是缩小，是扩大。** G7 不是在压学生，是在压教师，
顺带把学生的缺口遮住了。一条会掩盖待测对象缺陷的门，必须下架。

### 修法：硬门只装布尔不变量，程度放软分

| 门 | 判的是什么 | 性质 |
|---|---|---|
| G0 no-leverage | 这一对 (raw,ctx) 有没有受力点 | 是/否 |
| G1 quote-grounded | 有没有编造原文没有的锚点 | 是/否 |
| G2 locus-grounded | 落点是不是动作语境里的路径 | 是/否 |
| G3 anchors-kept | 承重锚点有没有丢 | 是/否 |
| G4 actionable | 有没有接地落点或验证命令 | 是/否 |
| G5 no-cause-inversion | 因果有没有倒 | 是/否 |
| G6 not-copy | 是不是照抄 | 是/否 |
| ~~G7 compressed~~ | ~~压到多少~~ | **连续量 → 软分** |

G7 改成软标准，由三个常数表达：

```js
export const COMPRESSION_TARGET = 0.5    // 产品要的压缩比。只记账，不拦稿
export const COMPRESSION_HARD_MAX = null // 硬门上限。null = 未装
export const COMPRESSION_SANITY = 1.0    // 荒谬线：比原文还长。进 advisory
```

**以后再训练到 0.5 时，把 `COMPRESSION_HARD_MAX` 设成 0.5 就重新装上**，
别的地方一行都不用动。这就是把它做成常数而不是写死的理由。

|---|---|---|---|---|

G2、G5 在这套 dev 上**一次都没触发**；G6 只触发 1 次。八道门实际只有五道在工作。

## 三、缺陷三（最关键）：G7 一直在掩盖学生的问题

见上表最后一行：学生在 G7 上**比教师还强**，在 G1/G3/G4 上全面落后，G1 是压倒性的一条。

### 学生的 G1 不是尺子的锅 —— 查过了

原本怀疑 G1 是尺子的归一化 bug（Python 点号模块 vs 文件路径）。查了 39 条命中、236 个凭空锚点：

- **176 个（74.6%）在 raw∪ctx 里连近似串都没有** —— 实打实的编造：
  `setdefaultLater`、`objectMergeById`、`call_strategy`、`findProxyForURLEx`、
  `myIpAddressList`、`isInSubnet`、`temp_abc123.py`、
  `/usr/local/bin/python/verfiona/preprocessing/preprocessing.py`
- 只有 60 个（25.4%）是近似串（`py476` / `__init__.py` / `init__` 这类碎片）

不是归一化问题，是**学生在编标识符**。

## 四、`tools/g1-guard.mjs` —— G1 的确定性后处理门

### 它为什么在数学上不可能让结果变差

```
稿子 -> G1 检查 -> 有凭空锚点 => 摘掉那处引用 => 还是不行 => 回退 raw（100% 无损）
```

最坏情况就是回退原稿，而那正是当前「G1 不过就整条丢弃」已经在做的事。

### 为什么不「修复」而是「摘除」

把凭空的 `init__` 改写成 raw 里真有的 `__init__.py`，看起来更聪明，
但那是**拿正则替模型编一个它没说过的断言**。这个仓库已经在这件事上烧过两次
（`tools/gold-forge2.mjs` 拿「raw 里最长的文件名」当落点，C1–C6 全过）。
摘除只会让稿子变短，绝不会让它变假。

### 四种策略实测（73 条有受力点）

| 模式 | 过门 | 软分 | 孤儿小句 | 空稿 |
|---|---|---|---|---|
| off | 25/73 = 34.3% | 0.5740 | 0 | 0 |
| **strip（默认）** | **45/73 = 61.6%** | **0.5836** | **0** | **0** |
| drop | 46/73 = 63.0% | 0.5925 | **60**（16 条稿） | 0 |
| sentence | 32/73 = 43.8% | 0.5126 | 0 | **14** |

`drop` 多挣 1 条，代价是 60 处「是 ，」这种残骸 —— 而硬门全过、软分还**升高**。
`sentence` 把 14 条稿删空。

**所以默认 `strip`**，并加了两样东西：

- **安全阀**：修复后正文不足原 40% 就原样退回
- **`orphanCount` 诊断量**。⚠ **不做成门**：教师自然稿自己也有孤儿
  （722 条里最大 8 个，10 条 ≥ 3），阈值卡在 3 会误杀教师。
  它没有判别力，只有**诊断力** —— 用来在修复策略之间选，不能用来判稿子合不合格。

### 全量 722 条教师稿

`467 -> 517` 过门（`+50`）。教师也会编锚点，这道门对两边都有效。

## 五、教师 prompt v5 —— **负结果，不采纳**

往 v4 里追加 G1/G3/G4 的门定义（`transfer/prompts/teacher3-zh.txt`），n=30 配对：

| | 过门 | 软分 | token 比 p50 |
|---|---|---|---|
| v4 | 21/23 = 91.3% | 0.7031 | 0.5261 |
| v5 | 18/23 = 78.3% | 0.6799 | 0.5031 |

配对四格：都过 18 · 只 v5 过 **0** · 只 v4 过 **3** · 都不过 2。
McNemar χ² = 1.33，**不显著**，但方向是更差。

**结论：教师的剩余失败不是「没被交代」。** 把门的定义写进 prompt 不是杠杆 ——
v5 反而让稿子压得更狠（770 vs 898 字），于是丢了更多锚点。
这正好说明压缩与保真之间的张力是**真实存在**的，不是提示词能消掉的。

v4 仍是生产提示词。

## 十、过了 G1 门之后还剩什么 —— **没有第二块机械可回收的分数**

学生过完 G1 门之后还剩 28 条不过（45/73 过）。逐条查了剩下的两类失败，
结论是**它们不是尺子的锅，也不是后处理能修的**。

### G4 actionable：14 条，**0 条是编命令**

原本以为这一门主要抓「编一条不存在的验证命令」。实测：

```
g4rows: 14 · fab(编造命令): 0 · noPathNoCmd(既无路径也无命令): 14
```

14 条**全部**是「稿子里既没有一个接地路径、也没有一条命令」。这是**模式混淆**，
不是事实错误 —— 学生把「压缩这段推理」做成了「复述这个任务」。

最典型的一条 `fox-it_dissect.util_pr70#b15`（软分 0.350 vs 教师 0.928）：

> We need to clean up the repo as described, re-read the issue, and confirm the test file changes.

96 个字，一个标识符都没有。这类失败**没有任何机械修法** —— 你要么替它写稿，
要么承认它就是没学会。

### G3 anchors-kept：16 条，15 条清洗后仍然失败

承重标识符一共 43 个，丢了 15 个。逐条比对「丢的那个在稿子里有没有近似串」：

| | 个数 |
|---|---|
| 稿里有近似串（含包含关系） | 2 |
| 编辑距离 ≤ 34% 的近形 | 1 |
| **稿里根本没有** | **30 / 33** |

不是拼错，是**整条信息没写进去**。

### 顺手查了一个尺子缺陷：反斜杠碎片锚点 —— **实测零影响，故意不改**

`anchorsOf` 会从转义字符串里抽出 `n\nprint`、`sys\nsys`、`history\` 这类中段碎片，
共 **1008 种、1290 次**。它们几乎不可能被稿子逐字复现，理论上会污染 G3 的分母。

**但实测影响是 0**：把这类锚点从承重集里剔掉之后重判，

```
dev 教师 变化 0 条 · dev 学生 变化 0 条 · 722 条教师稿 变化 0 条
```

所以**故意不改** `anchorsOf`。改它会让 G1/G3 在全部历史数据上的判定全部重算，
换来的收益是实测 0 —— 那不是改进，是给自己制造一次不可比的断层。

（同理，"碎片锚点" 这个假设本身也被否掉了：`CliRunner`、`recover_adapter`、`SPIN`
看起来是更长锚点的子串，但 `hasAnchor` 用的是 `includes`，保住长的就自动命中短的 ——
它们被判"丢失"时，包含它们的那个长锚点也一起丢了。所以那 7 条不是误判。）

### 结论

**G1 是唯一一块机械可回收的分数，已经拿完了。** 剩下的 G3（丢信息）和 G4（模式混淆）
都是真实的能力缺口。下一根杠杆只能是训练，不能再加门。

## 十一、Kaggle 为什么会一直 QUEUED

推送后卡了 **2 小时**才从 `QUEUED` 变 `RUNNING`。逐项排除了本地原因：

| 检查项 | 读数 |
|---|---|
| `kernel_session_id` | **空** —— 一个机器都没分到 |
| `get_accelerator_quota_statistics()` | `timeUsed 5031s / 21600s` = 23%，没超 |
| `timeReserved` | `0s` |
| `list_kernels()` | 只有 3 个内核，另两个是 10 月 7/8 号的旧 notebook，**没在抢卡** |
| `kernels_logs()` | **0 字符**（没机器就没日志） |

根因在 Kaggle 侧，不在内核。读了 `kaggle` CLI 源码：
**`kernels_push()` 只调 `save_kernel()`，从不调 `create_kernel_session()`**；
而 kagglesdk 里 `create_kernel_session()` 的文档字符串写着它是给 **interactive** session 用的。

**这是两条不同的车道**：网页里点开跑走 interactive（立刻派机器），CLI push 走 batch
（等调度器）。两者扣同一份配额，但 batch 会排队。

所以「手动开不会这样」不是错觉 —— 是那条路根本不排队。

**判断"正常排队"还是"卡死了"的四条**（都符合就只能等，取消重推只会重新排到队尾）：

1. 状态 QUEUED 且 `kernel_session_id` 为空；
2. `timeUsed` 远小于 `totalTimeAllowed`；
3. 没有别的内核在抢卡；
4. `kernels_logs()` 返回 0 字符。

`deploy/kaggle/start-rwkv7.py` 因此加了 `--wait`（轮询到终态 + 自动拉日志），
并把上面四条写进了它的文档字符串。
