# dsh-cot-form-b 压缩经济性审计与路线决议（2026-09-25）

> 依据：`669296b` 源码 + DeepSeek Harness 官方默认参数 + 用户提供的定价。
> **不使用用户会话里的缓存命中数据**——用户为第三方接入，该数据不可信；本文一律按官方默认口径推算。
> 行号为 `669296b`。「已证实」= 可指到代码行或官方文档；「推算」= 按公式代入，需真机复核。

## 摘要（结论先行）

1. **按官方默认参数重算，cfb 当前设计是净亏的**：宿主每次压缩成本 `C ≈ 34k~45k` token，
   代入 262k 会话模型后，cfb 比不压多花 **+1.5% ~ +4.3%**。只有 `maxTokens=16384` 且 thinking on（`C ≈ 70k`）时 cfb 才转正。
2. **单块压缩存在数学天花板**：`净收益 ≤ 0.5·r − 4·o − T`。实测平均块 `r = 1075` token 时天花板仅 **≈ 390 token**。
   压缩率只决定能否接近天花板，**不决定天花板本身**——因为原文是新生成内容，副模型第一次读，缓存里没有，按全价 1× 计费。
3. **当前设计的回本线是 `r ≥ 11·o + 2·T ≈ 3635` token**（o=329 实测）。实测平均块 1075 ⇒ **每块净亏 1280 token**。
4. 四条候选路线的裁决见 §四。**跨轮批量（batching）被否决**：延迟造成的收益衰减（≈860 token/块）
   比批量摊薄省下的（≈80 token/块）大 10 倍。
5. **待办**：唯一能同时满足「覆盖 2/3 的块」与「每块盈利」的杠杆是**副模型与主模型解耦计价**（§五 路线 1）。
   在它落地前，「覆盖率」与「盈利」在数学上不可兼得。
6. ⚠ **本文所有以 token 计的数字都依赖一个未定的换算**：chars/token 到底是 2.57 还是 1.67，仓库内无 trace.log 无法裁定。
   两种口径差 1.5 倍，回本门槛因此是 6,070 或 9,342 字符。**阈值类决策必须等真机数据**，见 §6.3。

## 三、单块压缩的数学天花板（本文最重要的结论）

**移除一个 token 的价值 V**：

```
V = 1 + (C_call + C_rebuild) / room ≈ 1 + (28k~37k + 47k) / (146k~168k) ≈ 1.45 ~ 1.58
```

取 **V = 1.5**（该会话最终会触发压缩）。**若会话从不触发压缩，V ≈ 1.0 ~ 1.1，此时压缩必然亏。**

**单块净收益**：

```
净收益 = V·(r − o′) − (r + 4·o + T)
       = 1.5(r − o′) − r − 4o − T
       = 0.5·r − 1.5·o′ − 4·o − T          …(o′ = 实际保留 token，o = 实际输出 token)

天花板（o′ → 0, o → 0）= 0.5·r − T
```

**为什么这是硬墙**：`r` 是主模型刚生成的新内容，副模型第一次读，**缓存里没有，按全价 1× 计费**。
所以成本侧至少是 `r`，而收益侧上限是 `1.5r`，差额上限就是 `0.5r`。
**任何压缩率优化、prompt 优化、批量优化都改变不了 `0.5r` 这个上限。**

**代入实测均值** `r = 1075` token（对应约 2,763 字符）、`o = 329`：

> ⚠ **chars/token 口径未定，见 §六**。按 (2,763 字符 / 1,075 token) 反推是 **2.57 字符/token**（约合 0.39 token/字符）。
> 一个可用的交叉验证：`src/config.js:65` 自己写着「`birthMinChars` 3100 对英文 ≈ 930 token、对中文 ≈ 1,860 token」，
> 即英文 **3.33** 字符/token、中文 **1.67** 字符/token。**2.57 正好落在两者之间**，与「代码+中英混合」的内容形态吻合，
> 因此 2.57 比纯中文的 1.67 更可能是这批块的实际值——但 1,075 token 这个数本身来自外部 trace，仓库内无法复核。
> 换算成字符门槛时按 **1.67~3.33 的区间**取，见 §6.3。

| 方案 | o（输出） | o′（保留） | 成本 | 收益 | **净/块** |
|---|---|---|---|---|---|
| 现行副模型改写 | 329 | 329 | 2,399 | 1,119 | **−1,280** |
| 语义选句（1a），保留 24% | 35 | 259 | 1,223 | 1,224 | **≈ 0** |
| 语义选句（1a），保留 19% | 35 | 200 | 1,223 | 1,313 | **+90** |
| 电报化（1b），o=60 | 60 | 60 | 1,323 | 1,523 | **+200** |
| 副模型压 10k 大块 | 329 | 329 | 11,324 | 14,507 | **+3,183** |

**回本条件**：`0.5r = 5.5o + T` ⇒ **`r ≥ 11·o + 2·T ≈ 3635` token**（o=329）。
换算成字符门槛：按中文 1.67 字符/token 是 **6,070 字符**，按实测 2.57 是 **9,342 字符**，
按英文 3.33 是 **12,105 字符**。当前 `birthMinChars` 默认 **3100**（`src/config.js:60`）——
**整个区间内都远低于回本线。**

## 四、四条候选路线的裁决

### 路线 A：确定性抽取（纯代码，零 LLM）— **否决**
- 用户判断：非大模型手段无法理解语义，无法精准识别，必然信息损失。**采纳。**
- 补充：召回率指标本身用同一个提取器度量，属自证，不能作为质量证据。
- 唯一保留用途：**失败降级路径**（副模型超时/超长/无收益时，比原文放行便宜）。

### 路线 B：主模型自写摘要 — **否决（有实证）**
- ReasonIF 基准：所有被测推理模型（含 DeepSeek-R1）在**思考过程中**的指令遵守率 **< 25%**，且题目越难遵守越差。
  同样指令放在最终回答里平均 57.3%，放在思考里只有 15.6%；要求在思考里按 JSON 写，遵守率 **0**。
- "Let Me Speak Freely?"：格式限制会显著降低推理能力，限制越严降得越多；先自由推理再转换格式才基本不掉分。
  在思考里硬插「要点」正是把格式要求塞进推理过程本身。
- DeepSeek R1 论文自述对提示词敏感，few-shot 会稳定降低表现。
- 改放最终回答不可行：agent 场景下多数轮次是「思考 → 调用工具」，没有文字回答。
- **注**：此前提出的「占 15%」是假设值、非实测，特此更正。

### 路线 C：副模型只压大块 — **有效但覆盖率不足**
- 经济上唯一在当前口径下明确盈利（10k 块净 +3,183）。
- 但 1 万 token ≈ 2.6 万字符，实测平均块仅 2,763 字符 ⇒ **能触发的块极少**，达不到「覆盖 2/3」的要求。
- 附带要求：`prompts.js` 长度规则 8「宁可超出目标」与硬上限冲突，大块路线必须改成 `max_tokens` 硬上限，
  超限按失败降级处理。

### 路线 D：跨轮批量（batching）— **否决（本轮新算，推翻上一轮建议）**
> **更正**：上一轮建议了此路线，只算了批量摊薄、漏算了延迟成本。补算后结论反转。

**批量能省的**：
- 模板 T 与序号开销摊薄：单块天花板每块 `0.5×1075 − 8 = 530`，三块合并每块 `535`，**每块只多 5 token**。
- 加上跨轮冗余把保留率从 24% 压到 20%：三块净 +437，单块三连做净 +201，**每块多赚 ≈ 80**。

**延迟要亏的**（块 i 等到第 i+2 轮才被压，中间主模型读的是未压缩版）：
- 块 i 少赚 2 轮 × (1075−215) × 1.0 = **1,720**
- 块 i+1 少赚 1 轮 × 860 = **860**
- 三块合计 **2,580**，**每块 860**

**净：每块 +80 − 860 = −780。差 10 倍，不是边际差异。**

**唯一例外**：同一轮请求内出现多个 reasoning block 时，合并零延迟、可白赚。值得在 trace 里查频次，但不能作主方案。

### 路线 E：语义选句（1a）— **保留，但先离线评估、不接线上**
模型只输出保留哪些句子的**序号**，本地按序号从原文 `slice()` 原样拼接。

三个性质由**代码**保证，不依赖模型守规矩：

| 性质 | 为什么成立 |
|---|---|
| 零幻觉 | 输出每个字都来自原文，模型只给下标 |
| 损失可计算 | 丢了哪几句、多少 token，全部已知，可写进 trace |
| 可硬门控 | 用 `src/fidelity.js` 提取标识符/路径/数字/报错串逐一核对；缺一个 ⇒ 放弃压缩、原文放行 |

越界序号 / 格式错乱 / 超时 ⇒ 一律回退。原文永远在 CAS（铁律③不变）。

**这是「信息不丢失」能达到的最强形式**：不是「无信息损失」（任何有损压缩做不到），
而是**损失是纯遗漏、可度量、有硬门控兜底、且可 100% 找回**。
「主模型性能不受损」只能实测、无法承诺；但选句版可**离线**测（归档里有原文），且不依赖不可信的缓存数据。

## 五、决议与待办

### 已定
1. 放弃路线 A / B / D。
2. 路线 E 作为下一步实现对象，但**先做离线评估器，不改线上行为**：
   对归档原文跑选句压缩，产出「纯遗漏式压缩最多能删多少而不碰标识符」的真实分布。
   该数字决定后续所有决策，且只依赖插件自己记录的数据。
3. 失败降级：副模型超时 / `length` / `no-token-gain` 时走确定性抽取，而非原文放行；
   同时排查 ≥ 28% 的归档失败率。

### 待办（阻塞项）
- **副模型与主模型解耦计价**（用户定为「之后单独设计一个接口，允许压缩模型跟随主模型或固定自定义」）。
  这是**唯一**能同时满足「覆盖 2/3 的块」与「每块盈利」的杠杆：副模型单价降到主模型 1/5 时，
  成本 `0.2×(r + 4o) + T` 从 2,399 降到 486，现行设计单块从 −1,280 转为 **+633**。
  **在接口落地前，覆盖率与盈利不可兼得。**

### 仍未解的老问题（v11.11 遗留）
A/B 测试、`finishWaitMs`、token 系数、`birthMinTokens`、econ / `identifierRecall` 门控、缺陷 B、`recoverSnapshot`。

### 6.3 阻塞项（必须先有真机数据才能定）

1. **chars/token 实测值**：`src/config.js:65` 给出的区间是中文 1.67 / 英文 3.33，反推值是 2.57。
