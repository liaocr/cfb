# 第三批：增量编译通道，以及产品架构路线

2026-09-22。基于第二批源码继续开发；未推送、未部署、未调用外部模型。

## 一、结论先行

这次做了两类工作：

1. **缺陷修复**：截断证据被整条标成已覆盖、信封丢失结果序号、排队期间输入可变、未来快照回流、长分支名碰撞。
2. **架构实验**：进程内、会话＋分支级的有界编译通道；在飞任务不打断，待编译只保留最新到达的一项；出队时根据成功提交的快照重新计算增量。

新通道通过 `stateCompileQueue:true` 启用，**默认关闭**。安全修复无须开启这个实验。

不增加主流 finish 等待，不增加每个任务的模型调用数，不改六栏输出、工具调用块和 surface 协议。等待＋传输共用原 timeoutMs，排队不另送一份 8 秒。

**这不是完整增量引擎的最终形态**：它合并的是压缩机会，不是把多个原始推理合成一份摘要；没有跨任务共享模型输出，没有把晚到证据放回早先的推理截面。

## 二、从代码里找出的实际问题

### 2.1 截断片段不能代表整个结果事件

`buildEvidenceEnvelope()` 将工具结果裁到 1200 字符并打 resultTruncated 标记，但 birth 提交 coverage 时使用裁剪前 toolsForPrompt 的 resultSeq。因此，模型只见过前 1200 字符，整个事件却可能获得“下轮不用再发”的权限。

修复：

- 提交以实际生成的信封 tools 为准；
- 仅结果存在、状态终结、未截断、resultSeq 合法的事件获得覆盖权限；
- failed 且完整可见的结果仍是证据，不因为失败就丢弃；
- pending、running、缺结果和截断片段均不获得整条省略权限；
- `memoryPolicyVersion` 升至 **3**，policy 1/2 的正文保留、旧覆盖集合撤销。

代价必须明确：长工具结果可能反复进入编译输入。本轮不通过错误覆盖换取漂亮的 token 数字。真正的解决方向是后文的**范围级证据回执**。

### 2.2 信封曾丢失 resultSeq

适配器已提供结果序号，但信封构造只保留调用 seq。这样后续任何基于真实结果身份的增量过滤都无法可靠执行。

现在 resultSeq 保留在不可变工具记录里；没有拿调用 seq 冒充结果 seq。

### 2.3 顶层冻结不是输入冻结

旧信封只冻结最外层，tools、userAsks 及其记录还可以被修改。排队后这会把“已冻结截面”变成一个可变引用。

现在冻结工具记录、用户记录及其数组，以及 host 顶层。正常适配路径会先把事件转换成独立数据；不声称它能深度冻结任意插件传入的未知嵌套对象。

### 2.4 快照可能来自输入截面之后

增加 sourceCutSeq 检查：已知快照截面晚于本任务的冻结截面，不注入该快照。出队重算还有更严格门禁：截面必须已知，覆盖集合中也不能出现未来事件。

这避免“任务 A 排队期间发生的结果，被写成 A 当时已经知道”。

### 2.5 分支名截断造成身份碰撞

旧 normalizeBranchId 把分支名截到 120 字符。两个前 120 字符相同、后缀不同的分支会共享逻辑键，可能影响快照与调度。

现在保留完整分支键；文件名仍由原 safeKey 做长度控制及哈希。旧版截断键下的文件不会自动猜测归属或迁到其中一个分支。该极端情况可能暂时读不到旧快照，但不会错误串用。

## 三、已实现的架构：有界通道＋提交后增量重算

### 3.1 执行流程

```text
reasoning block-end
  ├─ 原文 CAS 归档（沿用既有门禁）
  └─ 冻结本次证据和配置
       └─ 按 sessionId + branchId 进入编译通道
            ├─ 无任务在飞：立即执行
            └─ 有任务在飞：最多保留一个最新到达的待编译任务
                 └─ 被替代任务不调用模型，原文仍在

执行任务
  → 检查原 timeoutMs 的剩余预算
  → 读取已成功提交的快照
  → 检查时间截面、完整可见性和精确覆盖
  → 若重算后的完整提示词更短，采用它；否则沿用原输入
  → 一次既有模型编译
  → 完整成功 + 原文归档成功才提交快照
  → 提交完成／失败后释放通道
  → 下一个任务才能重新计算增量
```

调度代码在 `compile-lane.js`，生产接线在 `index.js`，不是只有一个离线模拟器。

### 3.2 为什么不只是排队

仅串行调用会增加延迟，却仍可能发送排队前的完整旧信封。这里的关键是：**先等上一个提交完成，再决定本次哪些旧证据可以由快照承载**。

重算不会重新读取宿主事件，不会改变原始 cot、用户原话、runtime 或输入时间。只在足够可信且实际缩短提示词时，把精确已覆盖的旧工具正文换成完整快照。

最近八条工具证据的保留底线不变；新证据和 pending 不因为序号较小就省略。

### 3.3 有界与失败行为

- 每个键：最多一个在飞任务＋一个待编译任务。
- 每进程最多 128 个活跃键；达到容量拒绝新的压缩机会，不绕开门禁偷跑。
- 待编译过期、取消、被更新任务替代，都不调用模型、不推进覆盖。
- 模型失败、CAS 失败、快照锁竞争，下一任务不能借此过滤证据。
- 在飞任务不因新任务到达而被取消，避免丢弃已经支付的生成。
- 不同会话／分支独立执行。
- 这不是跨进程分布式队列；多进程共享快照时仍依赖文件提交锁。
- 若第三方自定义 distill 忽略取消并永不返回，通道不会假装它已结束再放行并发；生产 HTTP 路径使用原有取消／超时。

### 3.4 必须承认的取舍

“保留最新”按到达顺序，不保证该证据窗口覆盖了所有被替代任务。被替代任务的原始推理仍保留在主对话和归档中，不被声明为已编译。它也没有一个未来必然补编译的承诺。

因此减少编译请求，可能牺牲某些块的即时／迟到压缩机会。**主对话后续输入可能增加**。此实验不能默认被判定为总成本更低，更不能自动推断任务成功率上升。

默认关闭正是为了将确定的安全修复与尚待真实任务验证的调度策略分开。

## 四、实验与验证

新增 `incremental.selftest.mjs`：**29 项检查**。全量 **1032 通过、0 失败、1 宿主相关检查跳过，11 套件**。

涵盖：队列替代、取消、到期、容量、幂等释放、会话隔离、原文保留、提交屏障、未来截面拒绝、失败保留证据、覆盖升级迁移、长分支身份与实际 HTTP 传输。

撤回 8 项修复后，新套件均检测到失败，随后恢复源码。包括提前释放通道、取消出队增量重算、给截断结果覆盖权限等。

### 本地 HTTP 突发样例

条件：三个重叠的 birth 任务；每个初始包含 30 条不同的、800 字符工具结果；服务返回固定六栏文本。分别运行 JSON 和 SSE，均走真实 generateStateMemory／HTTP 路径，不是外部真实模型。

| 指标 | 通道关闭 | 通道开启 |
|---|---:|---:|
| 编译请求数 | 3 | 2 |
| 第一次提示词字符 | 29,173 | 29,173 |
| 后续请求提示词字符 | 29,173 + 29,173 | 10,647 |
| 编译侧总提示词字符 | 87,519 | 39,820 |

JSON 与 SSE 两种传输均得到同样结果。这个样例包含约 29k 字符输入，但本地固定响应不会模拟真实模型对大提示词的耗时或准确性。

样例内编译侧字符约减少 **54.5%**；不能解释为 token、账单或合格任务总成本减少 54.5%。被替代块保留的原文成本未计入这个表。

证据：`docs/archive/optimization-evidence-v3/{verification.txt,mutations.json,http-burst.json}`。

## 五、产品下一步架构：三层，而不是无限叠摘要

以下是待验证的工程设计假设，不包装成已经发表或已经证明的新理论；本轮只实现了其中的有界调度和增量重算基础。

```text
可信证据账本（发生了什么，原文在哪里）
             ↓
增量任务状态（哪些命题仍有效，哪些被修正）
             ↓
任务工作集视图（本次决策真正需要看到什么）
```

三层的职责分开后，省 token 不必等于删除证据，突出重点也不必等于把旧约束改写成更确定的断言。

### 方向 A：范围级证据回执——解决长结果反复发送

现有 coverage 的单位是“整个结果事件”，太粗。

设计单位改为：

`会话／分支 + 结果事件ID + 正文哈希 + 可见区间 + 视图策略版本`

例如模型只看过 [0,1200)，系统只允许复用这一区间形成的状态，不声称它掌握了 [1200,末尾)。同一事件正文改变、投影视图改变或区间改变，就不能复用旧回执。

收益假设：已处理片段不必重复发送；剩余片段仍可定向提供，长结果也能真正增量化。回执由宿主按实际输入产生，不能由模型正文自称。

验收：区间边界、哈希变化、失败／取消、跨会话同文、旧视图迁移都不能错误获得覆盖。必须先有这层，再考虑降低每轮工具尾部保留量。

### 方向 B：修正日志，而不是每轮重写全量状态

模型仍做一次六栏编译；增加可关联的条目引用与关系，交由确定性 reducer 判断能否应用。

核心操作是“新增命题／补充依据／记录分歧／明确修正”，不是笼统地“新记录覆盖旧记录”。证据权限、范围和身份来自宿主验证；渲染仍兼容六栏。

收益假设：减少每轮反复输出旧约束与旧状态，降低快照无限重复增长，也减少摘要被摘要时的漂移。

验收：没有匹配证据或范围时，不允许无依据 supersede；不允许仅靠文字相似度删掉同对象的不同命题。

### 方向 C：带依赖的工作集，让主模型更专注

不按“最近 N 字符”裁剪，而按当前决策依赖构造视图：

1. 当前目标和验收条件；
2. 仍适用的用户硬约束；
3. 当前阻塞项及其证据；
4. 已排除路径、适用范围与失效条件；
5. 下一次决策需要辨别的未知项。

历史细节进入可检索层。投影一旦没有携带某项证据的必要结论，就撤销对应省略权限，不能一边隐藏记忆、一边继续删它的原证据。

收益假设：主模型更容易把注意力放在当前差距，而不是反复解释已结束的探索。需要任务级验收，不能用“工作集看起来更短”代替。

### 方向 D：以合格任务总成本决定编译，而不是只看压缩率

本轮调度揭示了一个重要问题：跳过编译便宜，但把长原文带着走 55 轮可能更贵。

按已有相对价格输入 1、输出 4、缓存输入 0.02，一个简化比较是：

```text
跳过编译的净收益 ≈
  省下的编译输入与输出成本
  − 多保留原文的 token ×（后续未命中发送次数 + 0.02 × 命中次数）
  − 额外返工成本
```

这不是当前实现里的计费算法，因为还没有真实 tokenizer、缓存命中与后续使用次数。但它给出了下一步调度应该优化的目标：

- 高复用、预计长期驻留的状态优先编译；
- 很快过期、不会再次发送的材料不一定值得编译；
- 冲突／关键约束的价值不能只按字符数衡量；
- 任何省钱策略都受验收质量约束。

下一轮实验应同时统计主对话与编译调用的输入／输出／缓存成本、合格完成情况、纠错次数，而不只统计本插件的 promptChars。

## 六、全部路线完成后的产品形态

用户仍使用原来的对话与工具。内部是：可追溯原文 → 精确增量证据 → 可验证的状态修正 → 面向当前任务的工作集。

预期能同时减少重复发送、重复探索和错误坚持；旧细节可恢复，未知仍是未知，禁止仍是禁止。系统不再靠越来越长的看板“记住一切”，也不靠更长 finish 等待掩盖编译延迟。

这是目标，不是本轮已经实现的效果。CAS 镜像恢复、消息级迟到认领、范围回执、条目关系验证、工作集投影都还有后续开发。
