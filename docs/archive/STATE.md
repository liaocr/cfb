```
            H4 索引字节预算 · H5 先检索后丢弃 · V1 不拥有别人的工具集
```

**三条机制硬事实**
1. 改「**从未发出过**的那条消息」**免费**；改已发出的 = 全价重发（代价 ∝ 改动点之后）。
2. **请求侧不可改**（`deepFreeze` + cordis waterfall `next()` 不收参）⇒ 唯一可用的缝是**响应侧包流**。
3. **fail-closed 必须可计数**——拦下来要留痕，否则分不清"没发生"和"没工作"。

## 15. ② 改写桶根因（09-16 首轮，仪器 = boundary.jsonl 146KB，未碰大文件）

**结论：改写桶的根因是【宿主压缩】，不是我们的插件。**

### 证据
- 仪器：`~/.dsh/storages/boundary/boundary.jsonl`（146KB，785+ 条 observe，每条带 msgCount/bytes）
- **字段完整的 observe 624 条 ⇒ 同会话相邻对 600 ⇒ bytes 下降 26 次**
- 下降**形态只有两种**：
  1. **两段式大塌缩（18 次）**：`~800KB → ~570KB → ~250KB`，msgCount `219→166→58`（每次砍掉 30–55% 消息）⇒ **压缩**
  2. **会话启动噪声（8 次）**：`4.6KB→278B，mc 3→1，Δt=0` ⇒ **首请求结构，不是改写，必须剔除**
- **宿主压缩由宿主发起**：`dsh-boundary-plugin/index.js:810` 注释 `host compaction response: detect lifecycle events since last scan` ⇒ 我们只是"响应并归档丢失内容"；事件名 `compaction-support`(808) / `compaction-respond`(903,912,991) 均为 boundary 侧记录
- **CMB 外置 98 次、结算引擎 replace 均未产生 shrink** ⇒ 结算引擎打在未发送尾部，**不改前缀，前缀安全** ✓（设计正确性得到独立佐证）

### 成本定性（推翻"这是建模假象"的猜想）
压缩写在**头部** ⇒ 该点之后的前缀缓存全废 ⇒ 之后整段按全价重算 ⇒ analyzer 那句"shrink 按整个新 prompt 全价计"的 ASSUMPTION 对压缩事件**基本成立**（是上限但接近真值）。**11.4% 是真钱。**

### 可动杠杆（按性价比）
1. **降频**：每次压缩都要付一次全价重算 ⇒ **"少压几次、每次多压一点"优于"频繁小压"**（方向待验证宿主阈值配置在哪）
2. **计量**：给 edge 加"压缩次数 / 每次新 prompt 字节 / 该次全价重算当量"计数器 ⇒ 改写桶从假设变实测
3. **不可动**：compaction 由宿主发起，插件侧只能响应
