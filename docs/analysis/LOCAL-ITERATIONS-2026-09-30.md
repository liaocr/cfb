# 两轮零 API 迭代：真实原生宿主与有限修复策略（2026-09-30）

## 预注册（实现和新任务执行前）

基线 `aba9993`，746/0/1，23 套件，manifest 281，N1–N7 全零。用户批准前两轮纯本地实施，未批准任何主/副模型、评委、白盒训练或生产接管。

本机探测：没有 dsh 可执行文件，`@deepseek-ai/cordis` 和 `dsh-context-memory-bundle` 不可解析；不得用事件替身消掉原有跨包跳过。第一轮实际范围是仓库生产代码的原生 `createEvidenceHost`/publish/runLatest/验证/文件+JSON恢复闭环，另测生产 birth 模块的录制流接线；完整外部 DSH/Cordis 仍阻塞。

新任务不重用旧 32 场景：18 个任务、6 个实际传输配置族、6:6:6。故障形态取自已有 hedge/身份/指纹事故：主请求迟到、提前断言、模型或指纹不等价。用真实 loopback HTTP、真实计时器、独立 Node 工作负载进程复现，冻结判据和检查器文件。新任务仍是本代理编写的复现变体，不称独立人写泛化。三切分按传输族隔离；test 必须在所有候选固定且持久预占之后才执行。

强基线不是 idle/unchecked：所有路径都用同一冻结契约、相同宿主权限、最多 3 轮/2 次修复/同一检查预算、真实前置/验收/联合恢复。基线固定先调整等待窗口，再改为等待主请求完成；不会靠放宽模型身份判据取胜。

先冻结四个策略：
1. static-safe：固定诊断顺序 + 固定批准修复分支。
2. active-only：只替换为 EIG 诊断，分支保持固定。
3. routing-only：保留固定诊断，只按认证后验选择批准分支。
4. active-routing：EIG + 认证后验分支选择。

诊断仅二元检查，分支选择只收到宿主产生的诊断后验/回执概要，不收到任务族、故障标签、参考输出或失败散文。unknown、后验不够确定、恢复失败、冲突、截止、预算满都不能凭猜测启用因果分支。只有宿主显式调用 episode 入口才调度，不改默认插件行为。

可证伪预测：
- L1：发布、前置、落地、可判率和恢复应接近全覆盖；静态路径损失集中在第二修复分支选择，而不是未授权/无检查。
- L2：静态基线预计 12/18（训练/选择各 4/6），非 0；active-only 完成率基本不变，诊断检查更少。
- L3：routing-only 与 active-routing 预计 18/18；active-routing 不比固定诊断路由少完成任何任务，并减少诊断检查。若无改善/有负项/unknown，不入库，不修改判据凑结果。
- L4：外部 API 0、付费 0；旧正文/chunks 不变，N1–N7 全零；原宿主跳过保留；结果不推广到实际模型或 P1 分数。

## 归因与测量

统计发布率、可判检查数/unknown、真实落地动作、终态完成、失败后文件+JSON完整恢复、第二分支完成率、诊断数、修复数、工作负载进程/本机 HTTP 数。成功以实际工作负载事件序列/返回模型指纹与冻结目标判定，不以策略自报或 Likert 排序。

第一轮只执行 train/selection 基线，定位瓶颈；第二轮对已冻结四策略比较，复用基线原始记录，三切分逐项签名。保留每个真实执行的签名记录；盲测执行前持久预占，重建对象也不得再次搜索同族。

最终数字在执行后填入。所有测试放在仅 loopback、无外部路由的网络命名空间，移除代理/API/凭据环境，不读 keys.env，不安装依赖。
